# 跨境合规结论互认服务设计

境内外机构在汇款前同步完成反洗钱、贸易背景与跨境合规审核，但任何一方都不把完整客户档案复制给对方。本设计用**可验证的最小凭证**替代"口头说已审核"：原始材料留在各机构本地，跨境链路只交换伪名、摘要与签名。所有不确定情形一律阻断（fail-closed），付款前必须得出一致结论。

## 角色与信任

- 每个参与机构持有自己的 ed25519 密钥对，公钥在建立互认关系时登记（`registerPeer`）。
- 合规负责人可以暂停与某一机构的互认关系（`pausePeer`），暂停事件随事件流传播，双方同时停止签发与接受；恢复同理。
- 审计人员只接触门禁决策记录，不接触原始客户材料。

## 可轮换标识

客户与订单在跨机构链路上只以**成对伪名**出现（`IdentifierRotator`）：

```
pseudonym = HMAC(pair_secret, pair_id | epoch | local_id)
```

- **成对隔离**：同一客户对机构对 A↔B 与 A↔C 呈现不同标识，无法跨链路拼接。
- **可轮换**：轮换纪元递增后旧伪名不再用于新凭证；已签发凭证保持签发时的伪名，历史审计不受影响。
- 本地标识到伪名的映射只存在签发机构内部。

## 数字凭证

凭证字段（契约见 `contracts/credential.schema.json`）：

| 字段 | 含义 |
| --- | --- |
| `credential_id` | 内容摘要派生，防篡改、天然去重 |
| `issuer` / `audience` | 签发方 / 接收方机构标识 |
| `subject_ref` / `order_ref` | 客户与订单的成对伪名 |
| `order_digest` | 订单内容摘要，订单变更即与凭证脱钩 |
| `scopes` | 审核范围：`aml`、`trade_background`、`cross_border` |
| `rule_set_version` | 审核所用规则版本 |
| `list_epoch` | 签发时的共享名单纪元 |
| `evidence_digest` | 证据摘要的摘要，原始证据不出机构 |
| `not_before` / `not_after` | 有效期，一律归一化为 UTC |
| `restrictions` | 限制条件，如 `amount<=50000`、`corridor=CN>SG` |
| `idempotency_key` | 幂等键，重复请求返回原凭证 |
| `issuer_head` | 签发时签发方事件流水位 |
| `signature` | 对全部字段规范化序列化后的 ed25519 签名 |

凭证不含任何原始客户信息；接收方拿到凭证即可独立验签，但无法反推客户身份或证据内容。

## 事件与同步

每个机构维护**只增事件日志**（契约见 `contracts/event.schema.json`），事件类型：

- `CREDENTIAL_ISSUED` / `CREDENTIAL_REVOKED`：签发与吊销
- `ORDER_SUPERSEDED`：订单变更，旧凭证作废
- `LIST_UPDATED`：共享名单纪元递增
- `CHALLENGE_OPENED` / `CHALLENGE_RESOLVED`：质疑与补充核验应答
- `RELATIONSHIP_PAUSED` / `RELATIONSHIP_RESUMED`：互认关系暂停与恢复

接收方对每个签发方跟踪三个量：`appliedSeq`（已应用水位）、`announcedSeq`（对方宣称的水位）、`lastSyncAtMs`（上次同步时刻）。`syncFrom` 增量应用对方事件。凭证中的 `issuer_head` 与付款指令携带的水位声明（`noteAnnouncedHead`）让接收方即使离线后也能发现自己落后。

## 付款门禁

`gateDecision` 在付款前对某笔订单做最终判定，任一条件不满足即阻断并记录原因：

1. **验签**：签名有效、签发方可信、互认关系未暂停。
2. **凭证状态**：未吊销、未因订单变更作废。
3. **有效期**：当前 UTC 时刻落在窗口内（时区在入口处归一化，双方算的是同一时刻）。
4. **名单新鲜度**：凭证名单纪元不落后于本机构已知的共享名单纪元。
5. **范围覆盖**：可用凭证完整覆盖反洗钱、贸易背景、跨境合规三类审核。
6. **订单一致性**：凭证绑定的订单摘要与付款指令当前摘要一致。
7. **限制条件**：逐条评估，评估上下文缺失视为不满足。
8. **质疑**：无未决质疑。
9. **同步新鲜度**：与每个相关签发方的同步未超过时限，且已应用水位不落后于对方宣称水位——离线机构恢复后必须先同步再付款。

## 六类一致性场景

| 场景 | 机制 |
| --- | --- |
| 名单更新 | 共享名单纪元递增并随事件传播；旧纪元凭证判 `LIST_STALE`，需重新筛查签发 |
| 凭证吊销 | 吊销事件只增传播；接收方未同步到最新水位前门禁阻断（`SYNC_STALE` / `SYNC_BEHIND`） |
| 订单变更 | 订单摘要变化使旧凭证作废（`ORDER_SUPERSEDED`），凭证摘要与付款指令摘要不一致判 `ORDER_CHANGED` |
| 时区差异 | 所有时间携带时区标记并归一化为 UTC 毫秒比较，拒绝无时区时间 |
| 重复请求 | 幂等键相同且载荷一致返回原凭证；载荷不同判冲突，绝不产生两张凭证 |
| 机构离线恢复 | 只增事件日志支持增量追平；恢复后双方对同一笔付款得出相同结论 |

## 质疑与补充核验

接收方对凭证存疑时开立质疑（`openChallenge`，重复质疑幂等），未决质疑阻断该订单的付款门禁。签发方从事件流得知质疑后完成补充核验，以补充证据摘要应答（`respondChallenge`），接收方同步后重新评估。质疑不解决，付款不放行。

## 审计与最小披露

每次门禁判定都落一条审计记录：决策（放行/阻断）、原因码、所用凭证号、名单纪元、同步水位。审计人员按订单伪名检索（`auditTrail`），即可回答"这笔资金为何被放行或阻断"，而记录中只有伪名与摘要——与该交易无关的客户信息和其他交易都不出现。

## 仓库结构

- `src/identifiers.js`：可轮换成对伪名
- `src/credential.js`：凭证构建、签名与验签
- `src/service.js`：互认服务（签发、验签、质疑、吊销、暂停、同步、门禁、审计）
- `src/restrictions.js`：限制条件评估
- `src/time.js`：UTC 时间归一
- `src/crypto.js`：规范化序列化、摘要与 ed25519 签名
- `contracts/`：领域资料、凭证与事件的共享契约
- `fixtures/domain.json`：不含真实个人信息的领域示例
- `test/`：覆盖上述全部一致性场景

运行 `npm test` 可验证全部行为。
